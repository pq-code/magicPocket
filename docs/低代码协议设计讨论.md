# 低代码平台协议设计讨论

本文在「组件库 | 渲染器 | 控制器」三块结构下，讨论**协议分层**与各协议职责，作为设计讨论稿，不涉及具体实现细节。

---

## 一、当前三块结构简述

| 区块 | 位置 | 当前实现 | 职责概括 |
|------|------|----------|----------|
| **组件库** | 左 | materialArea、componentList、各组件 meta（Container/Form/Table…） | 提供可被编排的组件**定义**：type、名称、分组、图标、**属性配置结构**（供控制器渲染配置面板） |
| **渲染器** | 中 | RenderEngine、TypeRenderEngine、pageJSON 树、VueDraggable 画布 | 根据**页面描述数据**递归渲染组件树，支持拖拽、选中、删除；编辑态/预览态切换 |
| **控制器** | 右 | ControlPanel、PropsItem、各 OperatorPanel（Form/DlockContainer…）、useCodeConfig/collectProps | 根据当前选中节点的**属性结构**动态渲染配置 UI，与 pageJSON 双向绑定 |

**数据流**：组件库产出「组件元数据（含 props 描述）」→ 画布上的节点是「元数据 + 实例 props + children」→ 控制器消费「节点上的 props 描述」生成表单项并写回节点。  
**缺口**：元数据与实例之间没有统一 **Schema**；行为（如表单 onChange）是内联代码字符串，没有**行为描述协议**；组件间没有显式**通信协议**；多端/多人没有**协作协议**。下面按「协议分层」来收口这些能力。

---

## 二、协议分层思路

协议分层原则：**底层协议不依赖上层，上层可依赖下层**；同一层内协议尽量解耦，避免循环依赖。

```
                    ┌─────────────────────────────────────────┐
                    │  扩展协议 (Extension)                     │  ← 预留：插件、自定义协议
                    └─────────────────────────────────────────┘
                                          │
  ┌───────────────────────────────────────┼───────────────────────────────────────┐
  │ 应用层 / 业务协议                       │                                        │
  ├───────────────────────────────────────┼───────────────────────────────────────┤
  │  实时协作协议 (Collaboration)          │  行为描述协议 (Behavior)                │
  │  条件表达式协议 (Condition)            │  组件通信协议 (Component Communication) │
  └───────────────────────────────────────┴───────────────────────────────────────┘
                                          │
  ┌───────────────────────────────────────┴───────────────────────────────────────┐
  │ 描述层协议                                                                     │
  ├──────────────────────────────────────────────────────────────────────────────┤
  │  组件描述协议 (Component Descriptor)   ← 依赖 Schema / 扩展 Schema             │
  └──────────────────────────────────────────────────────────────────────────────┘
                                          │
  ┌───────────────────────────────────────┴───────────────────────────────────────┐
  │ 基础层协议                                                                     │
  ├──────────────────────────────────────────────────────────────────────────────┤
  │  Schema 描述协议 (Schema)    扩展 Schema 协议 (Extended Schema)                 │
  └──────────────────────────────────────────────────────────────────────────────┘
```

- **基础层**：定义「如何描述结构、类型、约束」——Schema 与扩展 Schema，与具体组件/业务解耦。  
- **描述层**：在 Schema 之上定义「组件长什么样、有哪些配置项、能接收什么」——组件描述协议，组件库与渲染器、控制器都依赖它。  
- **应用层**：在「已有组件与结构」之上定义「组件间如何通信、行为如何描述、条件怎么写、多人如何协作」——组件通信、行为、条件、协作。  
- **扩展层**：预留「自定义协议、插件协议」的挂载点，可依赖下层任意协议。

---

## 三、各协议职责与讨论点

### 3.1 Schema 描述协议（基础层）

**目标**：统一「可配置项」的结构与类型描述，便于校验、生成控制面板、序列化。  

**范围**：  
- 基础类型：string / number / boolean / enum / object / array 等。  
- 约束：必填、范围、正则、最大长度等。  
- 与具体 UI 控件解耦：Schema 只描述「是什么」，不强制「用什么组件渲染」（可由扩展 Schema 或控制器映射）。

**与三块关系**：  
- 组件库：组件 meta 的 props 描述应符合 Schema（或扩展 Schema）。  
- 渲染器：可选用 Schema 做运行时校验（如 props 是否符合组件描述）。  
- 控制器：根据 Schema 生成/选择表单项（input、select、switch…）。

**待讨论**：  
- 是否采用 JSON Schema 子集，还是自研一套更简化的 DSL（如只保留 type、key、label、default、required、options）？  
- 样式类配置（如 margin、padding）是否单独一套 StyleSchema，还是统一进通用 Schema？

---

### 3.2 扩展 Schema 协议（基础层）

**目标**：在基础 Schema 上扩展「业务/UI 语义」，不改动基础层即可增加新类型或新约束。  

**范围**：  
- 自定义类型：如 `color`、`size`、`slot`、`dataSource`。  
- 自定义约束：如「仅当某字段为 X 时必填」。  
- 与控制器约定：某种 type 对应哪种配置控件（如 type: 'dataSource' → 数据源选择器）。

**与三块关系**：  
- 组件库：可使用扩展类型描述组件 props。  
- 控制器：需能解析扩展类型并渲染对应配置 UI。  
- 渲染器：一般只消费「已解析后的值」，不直接依赖扩展类型名。

**待讨论**：  
- 扩展类型是「全局注册」还是「按组件/包注册」？  
- 版本与兼容：扩展 Schema 的版本如何与组件库版本对齐？

---

### 3.3 组件描述协议（描述层）

**目标**：完整描述「一个可被编排的组件」：身份、展示、配置结构、能力边界。  

**范围**：  
- 身份：type、id、version、package。  
- 展示：componentName、group、icon、description。  
- 配置结构：props 的「分组 + 项」，每项符合 Schema/扩展 Schema（如 divProps、titleProps、formItemProps）。  
- 能力：是否可嵌套、允许的子类型、默认插槽/具名插槽。  
- 与渲染器的约定：如何解析 type/npm 并加载组件（当前 type + npm.package + npm.exportName 已是一种隐式协议）。

**与三块关系**：  
- 组件库：是组件描述协议的**生产者**（注册、列表展示）。  
- 渲染器：是**消费者**（按 type/描述加载组件并传 props/children）。  
- 控制器：是**消费者**（按描述的 props 结构生成配置面板）。

**待讨论**：  
- 组件描述是「单文件静态导出」还是「运行时从注册表拉取」？  
- 是否显式区分「组件元数据（组件库用）」与「节点实例数据（画布用）」两种结构，并在协议里标明字段归属？

---

### 3.4 组件通信协议（应用层）

**目标**：约定组件与组件、组件与页面之间的**数据与事件**如何传递，避免到处 ref 或隐式耦合。  

**范围**：  
- 事件名与 payload 格式：如 `form.submit`、`table.selectionChange`。  
- 数据注入：如「表单值」「当前行」由谁提供、以什么 key 注入。  
- 可选：事件总线的命名空间、生命周期（仅当前页 / 跨页）。

**与三块关系**：  
- 组件库：组件描述里可声明「本组件发出/监听的协议事件」。  
- 渲染器：在运行时建立「事件→回调」或「数据源→注入」的绑定。  
- 控制器：可配置「当事件 A 时触发行为 B」或「数据来源选择」，即与行为描述、数据绑定联动。

**待讨论**：  
- 采用「全局事件总线」还是「父子/祖先-后代」的显式 props/emit？  
- 是否引入「数据域」概念（如 form 域、table 域）以限定作用范围？

---

### 3.5 行为描述协议（应用层）

**目标**：用结构化方式描述「当某事件发生时执行什么」，替代或包装当前的「假代码字符串 + new Function」。  

**范围**：  
- 触发：事件（如 onChange、onSubmit）或时机（如 mounted）。  
- 动作：赋值、调用接口、跳转、发事件、执行脚本等；可支持「动作链」。  
- 与条件表达式协议结合：仅当某条件成立时执行动作。

**与三块关系**：  
- 组件库：组件描述可声明「支持的行为事件列表」。  
- 渲染器：在挂载/事件处注入行为执行器。  
- 控制器：提供「配置行为」的 UI（如选择事件→选择动作→配置参数），并序列化为行为描述协议。

**待讨论**：  
- 第一版是「动作枚举 + 参数表单」即可，还是需要内嵌「表达式/脚本」？  
- 若保留脚本，是否统一走「条件表达式协议」做安全与解析？

---

### 3.6 条件表达式协议（应用层）

**目标**：统一「条件判断」的表示与执行，供行为、显隐、校验等复用。  

**范围**：  
- 表达式语言：是否采用 JSON 表达式的子集（如 `{ "eq": ["${form.a}", 1] }`），还是允许安全脚本（如 `value > 0 && form.visible`）？  
- 作用域：可引用的变量（当前表单、当前行、全局状态等）。  
- 安全：禁止访问、限制 API，避免任意代码执行。

**与三块关系**：  
- 组件库：可在组件描述中声明「显隐/禁用」依赖的条件键。  
- 渲染器：根据条件表达式计算显隐/禁用并更新视图。  
- 控制器：提供条件配置 UI（如「当字段 A 等于 B 时显示」），并序列化为条件表达式协议。

**待讨论**：  
- 表达式是「纯数据（JSON 表达式）」还是「受限脚本」？  
- 是否与行为描述协议共用一套「表达式 + 作用域」规范？

---

### 3.7 实时协作协议（应用层）

**目标**：多用户/多端同时编辑同一份页面描述时，保证一致性与冲突处理。  

**范围**：  
- 操作粒度：节点增删改、属性变更、选区/光标。  
- 同步模型：OT、CRDT 或 Last-Write-Wins + 版本号。  
- 会话与权限：谁在编辑、只读/可编辑、锁粒度（整页/节点）。

**与三块关系**：  
- 组件库：一般不改动，除非协作元数据里要带「组件版本」。  
- 渲染器：消费「远程操作」并更新 pageJSON / 选区；发出「本地操作」到协作服务。  
- 控制器：同渲染器，编辑即产生操作，需纳入协作序列。

**待讨论**：  
- 首版是否只做「全量推送 + 乐观锁」，暂不做 OT/CRDT？  
- 与现有 Socket.IO 的集成方式：单独协作 channel 还是复用现有 WS？

---

### 3.8 扩展协议（扩展层）

**目标**：在不改核心协议的前提下，允许插件或业务定义**新协议**或**扩展现有协议**。  

**范围**：  
- 协议注册：名称、版本、解析器/执行器。  
- 扩展点：在 Schema、组件描述、行为、条件等处的「扩展字段」或「钩子」。  
- 与三块关系：组件库/渲染器/控制器均可按「是否支持某扩展协议」做能力分级。

**待讨论**：  
- 扩展协议是「强约束（必须声明才生效）」还是「弱约束（未知字段透传）」？  
- 是否需要「协议能力声明」接口，供前端/IDE 做提示与校验？

---

## 四、协议与三块的对照表（讨论用）

| 协议 | 组件库（左） | 渲染器（中） | 控制器（右） |
|------|--------------|--------------|--------------|
| Schema | 按 Schema 描述 props | 可选校验 | 按 Schema 生成配置 UI |
| 扩展 Schema | 使用扩展类型 | 透传/校验 | 解析扩展类型并渲染控件 |
| 组件描述 | **生产**组件描述 | **消费**加载与传参 | **消费**生成配置面板 |
| 组件通信 | 声明事件/数据 | 建立绑定、派发事件 | 配置通信关系 |
| 行为描述 | 声明可配置行为 | 执行行为 | **生产**行为配置 |
| 条件表达式 | 声明条件键 | 计算显隐/禁用 | **生产**条件配置 |
| 实时协作 | — | **生产+消费**操作 | **生产**操作 |
| 扩展协议 | 注册/使用扩展 | 可选解析扩展 | 可选解析扩展 |

---

## 五、建议的落地顺序（供讨论）

1. **Schema + 扩展 Schema**：先定「配置项」的通用描述方式，再让组件库的 props 与控制器的表单项统一到该协议。  
2. **组件描述协议**：把当前「type + props 结构 + npm」显式化为一份文档化协议，便于渲染器与控制器对齐。  
3. **条件表达式协议**：先做「简单条件（字段等于/存在）」，再考虑表达式 DSL 或安全脚本，供显隐、行为分支使用。  
4. **行为描述协议**：在现有「假代码」基础上，增加「动作枚举 + 参数」的结构化描述，与条件表达式结合。  
5. **组件通信协议**：在行为与数据绑定需求明确后，再定事件名与数据注入约定。  
6. **实时协作协议**：在单机编辑稳定后，再引入操作序列与冲突策略。  
7. **扩展协议**：在核心协议稳定后，再开放扩展点与注册机制。

---

## 六、小结

- **三块**：组件库（左）、渲染器（中）、控制器（右）的边界保持清晰；协议按「基础 → 描述 → 应用 → 扩展」分层，避免循环依赖。  
- **先统一「描述」**：Schema + 组件描述协议，让左中右对「组件长什么样、配置长什么样」有一致语言。  
- **再补「行为与协作」**：条件表达式、行为描述、组件通信、实时协作，按需分阶段引入。  

本文档仅作设计讨论用，具体字段格式、命名与实现可在讨论定稿后另写协议规范（如 `docs/specs/schema.md`、`docs/specs/component-descriptor.md` 等）。
