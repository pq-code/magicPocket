# 所见即所得与双通道输出方案

本文讨论：**中间画布像设计软件一样可编辑**、**用 JSON 描述设计内容**、**根据 JSON 既生成代码又给渲染内核渲染**，从而实现跨平台部署。与当前三栏（左组件库、中渲染器、右属性）结构对齐，给出实现思路与取舍。

---

## 一、目标再澄清

| 目标 | 含义 |
|------|------|
| **所见即所得** | 画布上看到的，就是最终页面效果（或高度一致）；编辑时即预览。 |
| **中间像设计软件一样可编辑** | 不仅右侧改属性，还能在画布上**直接操作**：选中、拖拽排序/位置、缩放、对齐参考线等。 |
| **JSON 描述设计** | 一份 JSON 是「页面 + 组件树 + 属性 + 布局」的唯一描述，可存、可传、可版本。 |
| **双通道输出** | ① **代码生成**：JSON → 生成 Vue/React/HTML 等源码，部署为独立项目；② **渲染内核**：JSON → 运行时直接解释渲染，不生成源码，适合嵌入/多端。 |
| **跨平台部署** | 同一份 JSON 可导出为 Web 项目、小程序、H5、Electron 内嵌等，由「生成代码」或「对应平台的渲染内核」负责。 |

---

## 二、整体架构：一 JSON，双通道

```
                    ┌─────────────────────────────────────────────────────────┐
                    │                    设计器（当前应用）                      │
                    │  左：组件库    中：画布（所见即所得 + 可编辑）    右：属性  │
                    └─────────────────────────────────────────┬───────────────┘
                                                              │
                                        唯一数据源：pageJSON（树形 JSON）
                                                              │
                    ┌─────────────────────────────────────────┴───────────────┐
                    │                                                         │
            ┌───────▼────────┐                                    ┌───────────▼──────────┐
            │  通道 A：代码生成  │                                    │  通道 B：渲染内核     │
            │  JSON → 编译器   │                                    │  JSON → 运行时解释   │
            │  → Vue/React/   │                                    │  → 同一套或轻量内核  │
            │  HTML 项目      │                                    │  → 嵌入任意宿主      │
            └────────────────┘                                    └─────────────────────┘
                    │                                                         │
            ┌───────▼────────┐                                    ┌───────────▼──────────┐
            │ 部署为独立仓库   │                                    │ 部署为运行时包       │
            │ 可二次开发      │                                    │ 多端复用同一 JSON   │
            └────────────────┘                                    └─────────────────────┘
```

- **设计器内**：左中右不动；中间画布 = 当前 RenderEngine 的增强版，既「渲染」又「编辑」，数据源只有 pageJSON。  
- **JSON**：必须同时满足「设计器编辑」「代码生成」「渲染内核」三者的需求，因此要在协议里预留布局方式、尺寸、约束等（见下）。

## 三、中间「像设计软件一样可编辑」要怎么做

### 3.1 当前中间已经有的

- 从左侧拖组件到中间，写入 `pageJSON.children`。
- 列表型拖拽排序（VueDraggable，同一容器内排序）。
- 点击选中 → 右侧显示属性，可改 props；删除在组件 tag 上。
- 画布与 pageJSON 双向同步，已是「所见即所得」的雏形。

### 3.2 还缺什么才像「设计软件」

设计软件常见能力与在你们架构下的对应关系：

| 能力 | 含义 | 实现思路 |
|------|------|----------|
| **选中与高亮** | 点击/框选，当前有点击选中；可加强框选、多选。 | 保持 currentOperatingObject；可选：多选列表、框选选区。 |
| **直接拖拽位置/顺序** | 已有列表内排序；若要做「自由定位」需布局模型支持。 | 见下「布局模型」。 |
| **缩放 / 改变尺寸** | 选中后拖拽手柄改宽高。 | 需在 JSON 中存 layout 信息（宽高/约束）；组件包一层「编辑壳」提供手柄。 |
| **对齐参考线 / 吸附** | 拖拽时出参考线、自动贴齐。 | 画布层计算与组件矩形的关系，不一定要进 JSON；可先做编辑器辅助。 |
| **双击/内联编辑** | 如标题、文本在画布上直接改。 | 选中后根据 type 切到「内联编辑」模式，改完写回 node.props。 |
| **撤销/重做** | 已有 historyOperatingObject，可加强为针对 JSON 的 undo/redo。 | 基于 pageJSON 快照或操作序列。 |

要「最好」实现，需要先定一个**布局模型**，再决定画布编辑做到哪一步。

### 3.3 布局模型：决定「中间能编辑到什么程度」

当前更像是**流式/文档型**：同一层级用 VueDraggable 排序，子级塞进容器 slot，没有显式的 x/y/w/h。要像 Figma/Sketch 那样自由拖位置和改尺寸，就需要在 JSON 里带**布局信息**。

两种常见取舍：

| 方案 | JSON 中布局 | 画布编辑方式 | 代码生成 / 渲染内核 |
|------|-------------|--------------|----------------------|
| **A. 保持「流式 + 顺序」** | 只有树形 + 顺序，无坐标 | 继续列表拖拽排序；尺寸可交给 CSS（如 flex 占比、grid）、或简单 width/height 字段 | 生成带 class 的模板；内核用同一套布局组件 |
| **B. 引入「自由布局」** | 节点带 position/size（如 x,y,w,h）或 constraints | 画布上拖拽改位置、拖手柄改宽高；可选参考线/吸附 | 生成绝对/相对定位样式或 CSS Grid；内核需支持同一布局协议 |

**建议**：

- **短期**：采用 **A**。在现有树形 + 顺序基础上，为需要「可调尺寸」的组件在 props 里加少量布局相关字段（如 `width`、`flex`、`span`），右侧属性面板可编辑；画布上暂不做拖拽改尺寸的手柄，这样实现成本低、与现有 JSON 兼容。
- **中期**：若确实要「设计软件感」，再选 **B**：在节点上增加可选 `layout: { x, y, w, h }` 或 `constraints`，画布层包一层编辑壳（选中框 + 手柄），编辑壳只存在于设计器，渲染内核只读 layout 做定位。

无论 A 还是 B，**都建议在协议里显式区分**：

- **编辑器专用状态**（如选中、多选、参考线）：不写进持久化 JSON，只存在内存或单独 editorState。
- **运行时需要的描述**（树、props、layout）：才写入 pageJSON 并参与代码生成与渲染内核。

这样同一份 JSON 既适合设计器，也适合「生成代码」和「渲染内核」两种通道。

## 四、JSON 如何同时服务「编辑」「代码生成」「渲染内核」

要让双通道都能用，JSON 需要满足：

1. **无歧义**：组件类型、父子关系、属性、布局（若用）都能从 JSON 唯一还原。
2. **可扩展**：新组件、新属性、新布局字段能加而不破坏老解析器。
3. **可裁剪**：渲染内核可以只关心「树 + props + layout」，不关心组件库的 icon、group 等；代码生成可以只关心「要生成什么技术栈」。

建议把 JSON 在概念上分成两层（存储时可以仍是一个根对象）：

| 层级 | 内容 | 谁用 |
|------|------|------|
| **页面根** | type、title、version、metadata、layout（全局布局类型、栅格等）、children | 设计器、代码生成、内核 |
| **节点** | type、key、props、children、npm、**可选 layout**（位置/尺寸/约束）、可选 version/capabilities | 设计器、代码生成、内核 |

这样：

- **设计器**：编辑时读写整棵树，可选把 editorState（选中 id 等）单独存。
- **代码生成**：遍历树，按 type/npm 映射到目标技术栈的组件与 props，按 layout 生成样式或 class。
- **渲染内核**：同一套 JSON，用「内核自己的组件注册表」按 type 渲染；若内核是 Vue，可复用当前 TypeRenderEngine 的思路；若是别的运行时，就换一套组件映射。

**跨平台**的含义就是：

- **通道 A**：同一 JSON → 不同代码生成器 → Vue 项目、React 项目、静态 HTML 等。
- **通道 B**：同一 JSON → 不同平台的渲染内核（Web Vue、Web React、小程序、Electron 内嵌等），内核只负责「解析 JSON + 本地组件注册表 + 布局」。

## 五、双通道的具体实现思路

### 5.1 通道 A：JSON → 代码生成

- **输入**：pageJSON（或导出时的一次性快照）。
- **过程**：  
  - 遍历树，按 type/npm 映射到目标技术栈的组件名与 import。  
  - props 转为组件 props 或 attribute。  
  - children 递归为模板/JSX 子节点。  
  - 若有 layout，转为 style 或 class（如 grid/flex/绝对定位）。
- **输出**：源码文件（Vue SFC、React 组件、HTML+CSS）或完整项目脚手架。
- **部署**：用户把生成的项目拉到仓库，独立部署、可二次开发。

当前已有 CreateCode 等，可以逐步改造成「从 pageJSON 读树，按目标技术栈生成」，而不是写死一种形式。

### 5.2 通道 B：JSON → 渲染内核

- **输入**：同一份 pageJSON（或子树的 JSON）。
- **过程**：  
  - 内核有「组件注册表」：type → 实际组件。  
  - 递归：根 → children，每个节点按 type 取组件，把 props、layout 传入，children 递归渲染。  
  - 不生成源码，只做运行时解释。
- **输出**：在线的页面视图（若在 Electron 里就是当前中间画布；若在别的宿主就是嵌入的 iframe 或组件）。
- **跨平台**：同一份 JSON，换不同内核（Vue 内核、React 内核、小程序内核）即可跑在不同平台；JSON 协议统一，内核各自实现。

当前中间画布本身就是「Vue 版渲染内核」：TypeRenderEngine + 组件注册。要跨平台，就再做一个「React 内核」或「轻量 DOM 内核」，同一 JSON 不同入口即可。

### 5.3 如何选：生成代码 vs 渲染内核

| 场景 | 更合适的方式 |
|------|----------------|
| 需要把页面当独立项目、改源码、走 CI/CD | 通道 A：代码生成 |
| 需要内嵌到现有应用、多端同源、快速发版 | 通道 B：渲染内核 |
| 既要能导出项目又要能在后台/中台里直接跑 | 两套都做，共用一份 JSON |

建议：**协议和 JSON 先统一**，再分别做「代码生成器」和「各端渲染内核」，这样扩展成本最低。

## 六、建议的落地顺序

1. **定稿「页面 + 节点」JSON 协议**  
   包含：根节点、子节点字段；若有布局，约定 `layout` 形状（流式用 class/span，自由布局用 x/y/w/h）。和 `协议优化建议-参考博客.md` 中的 P0 对齐（TypeScript 类型 + 文档）。

2. **增强中间画布「设计软件感」（在现有基础上）**  
   - 保留列表拖拽与右侧属性；  
   - 可选：选中后内联编辑（如标题、单行文本）；  
   - 若采用自由布局，再加：选中框、拖拽手柄、参考线/吸附。  
   编辑器状态与 JSON 分离，不污染持久化。

3. **抽象「渲染内核」**  
   把当前「从 pageJSON 递归 + TypeRenderEngine」抽成独立模块（如 `RenderKernel`），输入 = JSON + 组件注册表，输出 = 视图。画布和后续「纯预览 / 嵌入」共用该内核。

4. **做一版「从 JSON 生成代码」**  
   先支持一种技术栈（如 Vue 3），从 pageJSON 生成单页或少量组件文件；验证 JSON 是否足够表达布局与属性。

5. **跨平台**  
   同一 JSON：  
   - 用 Vue 内核跑在 Electron/Web；  
   - 用代码生成导出 Vue/React 项目；  
   - 若有小程序/其他端，再为对应端做内核或生成器。

这样实现，**所见即所得**由当前画布 + 上述增强保证；**中间可编辑**由布局模型 + 编辑交互（列表/内联/可选自由布局）实现；**双通道与跨平台**由「统一 JSON 协议 + 代码生成 + 多内核」实现。

## 七、小结

| 问题 | 结论 |
|------|------|
| 如何实现所见即所得？ | 中间画布 = 用同一份 pageJSON 做实时渲染，编辑即改 JSON，已基本满足；可加强内联编辑、选中反馈。 |
| 中间如何像设计软件一样可编辑？ | 在保留列表拖拽与右侧属性的基础上，增加内联编辑、可选自由布局与拖拽/缩放手柄；布局模型（流式 vs 自由）决定 JSON 里是否带 x/y/w/h。 |
| JSON 如何设计？ | 一棵树（页面根 + 节点），节点含 type、key、props、children、可选 layout；协议显式、可扩展，编辑器状态不写进持久化 JSON。 |
| 如何实现双通道与跨平台？ | 通道 A：JSON → 代码生成器 → 各技术栈项目；通道 B：JSON → 各端渲染内核（Vue/React/小程序等）。同一 JSON，多生成器、多内核即可跨平台。 |

若你愿意，下一步可以具体定：**节点 + 根的 TypeScript 类型** 和 **layout 字段的最小约定**（流式 vs 自由二选一或兼容两种），再在现有 pageJSON 上逐步对齐。
